# Conductor × 中台双向同步与版本复盘计划

> 状态：讨论确认，待设计与实施  
> 更新：2026-07-27  
> 范围：Conductor ↔ 中台 → Temu、Amazon、Shopify、Etsy 等渠道

---

## 1. 目标

Conductor 定位为可替换的内容生产与分析工具，中台定位为商品、版本、发布、运营指标和复盘历史的唯一事实源。

需要建立完整闭环：

```text
Conductor 生成内部 Listing
→ 中台保存、选择和调整
→ 中台发布到具体渠道
→ 中台收集平台运营数据
→ Conductor 从中台拉取指定任务上下文
→ Conductor 形成复盘结论和候选优化方案
→ 中台确认后创建新渠道版本并再次发布
→ 持续记录版本和运营数据变化
```

本计划完成后，Conductor 本地 `output/` 和工作目录只是生产暂存、人工预览和短期缓存。中台确认完整持久化后，本地生成数据可以删除，不影响历史成果和后续复盘。

## 2. 核心原则

1. **中台是唯一事实源**：业务身份、正式版本、平台发布、运营数据和历史关系以中台记录为准。
2. **Conductor 只生产和分析**：生成内部 Listing、内容资产、复盘结论和候选优化，不直接决定哪个版本发布。
3. **内部 Listing 身份稳定**：同一个内部 Listing 的唯一 ID，例如 `abc`，在整个生命周期内不变。
4. **正式版本不可覆盖**：发布后任何修改都创建新版本，并保留父版本关系。
5. **候选方案与正式运营版本分离**：Conductor 产物是参考；中台选择并调整后的数据才形成渠道初始版本。
6. **线上事实与提交数据分离**：中台准备发布的数据、实际提交的数据和平台最终展示的数据分别保存。
7. **指标绑定对象与时间**：运营数据必须绑定具体 ChannelItem、统计周期、口径和对应生效版本。
8. **双向同步按任务执行**：Conductor 只拉取当前任务所需的不可变上下文快照，不镜像整个中台。
9. **文件必须实际持久化**：图片、视频和附件必须进入中台管理的对象存储，不能只保存本地路径或生成提示词。
10. **同步可验证、可重试**：使用文件哈希、幂等键、基础版本号和状态机保证完整性。

## 3. 领域模型

### 3.1 SKU 与内部 Listing

同一个 SKU 可以由 Conductor 产生多个独立内部 Listing，用于不同场景、创意、销售方案或目标人群：

```text
SKU-A
├─ InternalListing abc：日常使用方案
├─ InternalListing def：礼赠方案
└─ InternalListing ghi：功能卖点方案
```

`abc` 是内部 Listing 的稳定唯一 ID，不是单次执行 ID，也不是每次优化都会变化的版本 ID。

对装、多件装、套装或多 SKU 组合时，内部 Listing 绑定完整销售单位，而不是只绑定一个 SKU：

```text
InternalListing xyz
└─ SKU-A × 2 + SKU-B × 1
```

### 3.2 核心实体

| 实体 | 作用 | 是否可变 |
| --- | --- | --- |
| `InternalListing` | Conductor 产生的一套独立上架方案，ID 如 `abc` | 身份不变，状态可变 |
| `SourcePackage` | Conductor 为内部 Listing 生成的原始参考内容和资产 | 不可覆盖 |
| `ChannelItem` | 内部 Listing 在某个平台、市场、店铺中的线上实例 | 身份不变 |
| `ChannelRevision` | 中台确认的渠道完整内容版本，包含人工调整 | 发布后不可覆盖 |
| `Publication` | 某个 ChannelRevision 的实际提交和发布事件 | 不可覆盖 |
| `LiveSnapshot` | 平台在某个时间点实际展示的页面内容 | 不可覆盖 |
| `MetricSnapshot` | 指定时间范围的平台运营指标及原始口径 | 不可覆盖 |
| `ReviewRun` | Conductor 基于指定版本和指标完成的一次复盘 | 不可覆盖 |
| `SyncJob` | 中台与 Conductor 之间的一次生产、拉取或回传任务 | 状态推进 |
| `ArtifactManifest` | 文件清单、角色、永久地址、大小和哈希 | 不可覆盖 |

### 3.3 关系

```text
InternalListing abc
├─ SourcePackage SRC-001
├─ Temu ChannelItem CI-TEMU-001
│  ├─ ChannelRevision R1
│  │  └─ Publication P1 → LiveSnapshot S1 → MetricSnapshot M1
│  ├─ ReviewRun RV1
│  └─ ChannelRevision R2
│     └─ Publication P2 → LiveSnapshot S2 → MetricSnapshot M2
└─ Amazon ChannelItem CI-AMAZON-001
   ├─ ChannelRevision R1
   └─ ChannelRevision R2
```

同一个内部 Listing 可以进入多个渠道，但每个 ChannelItem 必须独立记录渠道版本、发布和运营数据，不能混合评价。

## 4. 版本生命周期

### 4.1 初始版本

1. Conductor 生成 `InternalListing abc` 和 `SourcePackage SRC-001`。
2. 中台保存原始参考内容和文件。
3. 中台选择该方案准备发布到 Temu。
4. 运营可以修改标题、图片顺序、价格或其他字段。
5. 修改后的完整数据形成 `ChannelRevision R1`。
6. `R1` 才是后续复盘的初始运营基线。

不得把 Conductor 原始参考内容与中台确认后的 `R1` 混为同一个版本。

### 4.2 复盘与新版本

```text
R1 发布
→ 收集 R1 生效期间的指标
→ Conductor 生成 ReviewRun RV1
→ 中台接受、修改或拒绝建议
→ 接受后的完整数据形成 R2
→ R2.parent_revision_id = R1
→ 发布 R2
```

复盘建议本身不能自动修改线上商品，也不能自动成为新渠道版本。只有中台确认后才创建 `R2`。

### 4.3 版本时间边界

每个发布版本必须记录准确的生效时间。如果 `R2` 于 2026-07-10 上线：

```text
R1 指标：2026-07-01 至 2026-07-09
R2 指标：2026-07-10 起
```

指标跨越多个版本且无法拆分时，标记为“混合版本数据，无法精确归因”，不得强行评价单一版本。

### 4.4 回滚

回滚也必须创建新的发布事件。可以复用旧版本的内容快照，但不能删除中间版本或改写历史。

## 5. Conductor 与中台职责

| 能力 | Conductor | 中台 |
| --- | --- | --- |
| 生成内部 Listing、文案、图片、视频 | 负责 | 保存和展示 |
| 生成多个场景或创意方案 | 负责 | 选择 |
| 人工调整 Conductor 产物 | 不作为事实源 | 负责并记录 |
| 创建渠道正式版本 | 提供候选内容 | 负责 |
| 发布到平台 | 不直接负责 | 负责或调用平台适配层 |
| 收集平台运营数据 | 不作为长期采集方 | 负责 |
| 保存页面快照和版本历史 | 可生成临时文件 | 负责 |
| 数据复盘和优化建议 | 负责 | 发起任务、保存和展示 |
| 是否采用复盘建议 | 不决定 | 中台或运营决定 |
| 长期文件存储 | 不负责 | 负责 |

n8n 或其他连接器可以负责传输和平台 API 编排，但不能替代中台成为业务数据事实源。

## 6. 出站同步：Conductor → 中台

### 6.1 出站内容

Conductor 推送内部 Listing 时，应同时发送结构化清单和实际文件：

- `internal_listing_id`
- Conductor 执行 ID
- SKU 或 SKU 组合
- 销售数量和组合关系
- 目标平台与市场建议
- 创意方向和商品事实快照
- 标题、描述、关键词和平台字段
- 图片、视频、脚本、报告和其他附件
- 每个文件的角色、格式、尺寸、大小和 SHA-256
- 规则、模板、模型和数据结构版本
- 生成时间

中台不得依赖 `D:\...` 或 `output/...` 本地路径作为永久文件地址。

### 6.2 推送状态

```text
generated
→ uploading
→ persisted
→ verified
→ local_deletable
```

只有中台完成结构化数据入库、文件持久化、数量核对、哈希校验和可下载验证后，才能返回 `local_deletable`。

### 6.3 幂等

每次出站同步携带稳定的幂等键。网络重试不能在中台创建重复的 InternalListing、SourcePackage 或文件记录。

## 7. 入站同步：中台 → Conductor

### 7.1 按任务拉取

中台先创建 `SyncJob`，Conductor 再按任务 ID 拉取上下文：

```text
中台创建 JOB-001
→ 指定 InternalListing abc、ChannelItem 和任务类型
→ Conductor 拉取不可变任务快照
→ 下载当前任务需要的文件
→ 校验文件数量与哈希
→ 在本地建立工作副本
```

支持的首批任务类型：

- 加载内部 Listing 继续生产
- 加载指定 ChannelItem 做数据复盘
- 加载历史版本做对比
- 加载未完成任务继续执行

### 7.2 复盘上下文

数据复盘任务至少包含：

- `internal_listing_id`
- `channel_item_id`
- `base_revision_id`
- `publication_id`
- `live_snapshot_id`
- `metric_snapshot_ids`
- 复盘时间范围
- 原始指标定义和平台口径
- 历史修改记录
- 对应文案、图片和视频文件
- 数据完整性与访问限制

### 7.3 本地工作目录

中台拉取的数据不属于 Conductor 新产物，不应直接写入正式 `output/`：

```text
workspace/{internal_listing_id}/{job_id}/
  同步清单.json
  商品资料/
  历史版本/
  平台页面/
  运营数据/
  原始素材/
```

Conductor 新生成的复盘结果和候选优化方案再写入 `output/`，成功回传中台后建立永久关系。

### 7.4 冲突控制

Conductor 回传时必须携带拉取时的 `base_revision_id`。如果中台当前版本已经变化：

```text
复盘基于：R3
中台当前：R4
结果：版本冲突，不得直接应用
```

中台可以要求重新拉取、重新复盘或人工确认，不得静默把旧结论应用到新版本。

## 8. 复盘闭环

### 8.1 输入

一次完整复盘由以下证据组成：

1. ChannelItem 的真实线上身份。
2. 中台确认并实际发布的 ChannelRevision。
3. Publication 和平台实际 LiveSnapshot。
4. 对应版本生效期间的 MetricSnapshot。
5. 原始 SourcePackage 和历史版本。
6. 标题、图片、价格、广告、库存等修改时间线。

### 8.2 Conductor 输出

`ReviewRun` 至少包含：

- 引用的 ChannelItem、版本、发布、页面快照和指标 ID
- 数据口径和完整性
- 原方案、中台版本和线上页面差异
- 漏斗问题及证据
- 结论置信度
- 待确认或无法归因项
- 优化优先级
- 建议修改字段
- 单变量测试计划
- 候选新文案或图片
- 继续观察、补货、调整或下架条件

### 8.3 中台处理

中台保存 ReviewRun 后，由运营选择：

- 不采用建议，仅保存复盘记录
- 部分采用并继续人工修改
- 全部采用
- 重新发起复盘

最终确认的数据创建新的 ChannelRevision，不修改原版本。

## 9. 数据存储

### 9.1 数据库

保存：

- 内部 Listing 与 SKU 组合关系
- ChannelItem
- ChannelRevision 与父版本
- Publication
- MetricSnapshot 及指标口径
- ReviewRun
- SyncJob
- 状态、时间、操作者和审计记录

### 9.2 对象存储

保存：

- 商品原图
- Conductor 生成图片
- 视频和音频
- Markdown、JSON、报告和脚本
- 平台页面截图
- 平台原始导出文件

数据库只保存中台永久文件 ID、地址和哈希，不保存 Conductor 本地路径作为永久引用。

### 9.3 原始数据与归一化数据

平台运营数据同时保存：

- 平台原始字段、值、单位和响应
- 中台归一化指标
- 指标定义、分母、币种、时区、归因窗口和数据来源

不得只保存归一化结果，否则可能丢失平台特有口径。

## 10. 接口草案

首期建议使用任务式 API：

```text
POST /api/v1/content-packages
GET  /api/v1/conductor/jobs/{job_id}/context
POST /api/v1/conductor/jobs/{job_id}/results
GET  /api/v1/assets/{asset_id}/download
```

要求：

- 中台生成或登记 `job_id`
- 写操作携带幂等键
- 大文件使用对象存储签名地址
- 返回 `schema_version`
- 返回文件清单和 SHA-256
- 结果回传携带 `base_revision_id`
- API 返回持久化与校验状态

Conductor 不直接连接中台数据库，也不持有平台长期账号、Cookie 或密钥。

## 11. 本地组件规划

后续可以增加 `middle-platform-sync-agent`，负责：

- 拉取任务上下文
- 下载并校验文件
- 建立本地工作副本
- 检查基础版本冲突
- 组装生产与复盘结果
- 上传结构化数据和实际文件
- 接收中台持久化确认
- 清理可删除的本地缓存

建议同时提供统一命令或内部服务接口：

```text
conductor pull --job JOB-001
conductor push --job JOB-001
conductor verify --job JOB-001
conductor cleanup --job JOB-001
```

命令名称仅为计划示例，实施时结合现有 Go 物料浏览器和 Agent 执行方式确定。

## 12. 实施阶段

### 阶段 1：标识与数据契约

- 确定 InternalListing、SourcePackage、ChannelItem、ChannelRevision 等实体字段。
- 确定 `abc` 的生成方、格式和幂等策略。
- 定义 JSON Schema、版本规则和文件清单。
- 定义平台、市场、店铺、SKU 和组合关系。

完成标准：同一个内部 Listing、渠道版本和文件可以在两个系统间无歧义识别。

### 阶段 2：中台持久化

- 中台接收 Conductor 内容包。
- 数据库存储结构化数据。
- 对象存储保存实际文件。
- 校验数量、大小和哈希。
- 中台可以完整展示和下载原始成果。

完成标准：本地删除前，通过中台能够恢复全部已上传数据。

### 阶段 3：中台选择、调整与发布版本

- 中台选择 Conductor 方案。
- 保存人工修改。
- 创建不可变 ChannelRevision。
- 记录 Publication、平台响应和 LiveSnapshot。

完成标准：能够回答“哪个版本在什么时间实际发布到了哪个平台商品”。

### 阶段 4：运营数据

- 采集并保存平台原始指标。
- 建立归一化指标和口径。
- 按 ChannelItem、版本生效区间和时间范围查询。
- 记录标题、图片、价格、广告和库存变更时间。

完成标准：运营数据不会跨版本混合归因，无法拆分时有明确标记。

### 阶段 5：反向拉取

- 中台创建 SyncJob。
- Conductor 按任务拉取上下文。
- 下载和校验文件。
- 建立独立 `workspace/` 工作副本。
- 支持历史版本和当前版本读取。

完成标准：本地没有历史 `output/` 时，Conductor 仍可从中台恢复上下文继续工作。

### 阶段 6：复盘和优化闭环

- Conductor 基于指定版本、页面快照和运营数据复盘。
- 回传结构化 ReviewRun 和候选优化资产。
- 中台显示证据、建议和版本差异。
- 中台确认后创建新 ChannelRevision。

完成标准：可以完整观察 `R1 → 指标 → 复盘 → R2 → 指标 → 复盘` 的变化历史。

### 阶段 7：可靠性与清理

- 增加幂等、重试、断点续传和冲突处理。
- 增加权限、审计和短期签名下载。
- 中台校验完成后允许清理本地缓存。
- 增加失败任务恢复和一致性检查。

完成标准：重复调用不产生重复数据，失败可以恢复，本地删除不造成成果缺失。

## 13. 验收场景

### 场景 1：同一 SKU 多方案

Conductor 为 `SKU-A` 生成 `abc`、`def`、`ghi` 三个内部 Listing。中台完整保存三套方案，只选择 `abc` 发布，其他方案保持未发布状态。

### 场景 2：中台修改后发布

中台选择 `abc`，修改标题和图片顺序后形成 `R1`。系统同时保留 Conductor 原始 SourcePackage 和中台正式 `R1`。

### 场景 3：多平台

`abc` 分别创建 Temu 和 Amazon ChannelItem。两个渠道拥有独立版本、平台商品 ID、页面快照和运营数据。

### 场景 4：复盘形成新版本

Conductor 基于 Temu `R1` 和对应指标生成 `RV1`。中台接受标题建议并创建 `R2`；`R1` 不被修改，后续指标只评价 `R2` 生效后的数据。

### 场景 5：反向恢复

删除 Conductor 本地历史产物后，中台创建任务。Conductor 通过 `abc` 和任务 ID 拉取完整上下文，在本地恢复工作副本并继续复盘。

### 场景 6：版本冲突

Conductor 基于 `R2` 工作期间，中台已经发布 `R3`。结果回传时检测冲突，不自动把旧结论应用到 `R3`。

### 场景 7：文件完整性

中台保存的图片、视频和报告数量、大小和 SHA-256 与 Conductor 清单一致，确认可下载后才允许本地清理。

## 14. 待确认事项

- `internal_listing_id` 由 Conductor 生成、中台生成，还是由调用方预分配。
- 同一个 InternalListing 是否允许跨平台复用，还是每个平台生成独立内部 Listing。
- 中台人工修改哪些字段必须产生新 ChannelRevision。
- 平台数据采集频率、最小时间粒度和历史保留周期。
- 大文件上传方式、对象存储和签名地址有效期。
- Conductor 身份认证、权限范围和审计要求。
- ReviewRun 是否只返回建议差异，还是同时返回完整候选版本。
- 当前本地 `output/` 与未来中台 InternalListing ID 的映射和迁移方式。

## 15. 暂不实施

本计划当前只用于统一方向和后续设计，不立即实施以下内容：

- 直接连接任何平台正式账号
- 自动发布或自动修改线上商品
- 自动接受 Conductor 复盘建议
- 自动删除尚未通过中台完整性校验的本地文件
- 未经确认迁移现有 `output/` 历史目录
