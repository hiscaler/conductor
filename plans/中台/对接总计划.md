# Conductor × 中台对接总计划

> 状态：第一阶段已定稿（单向薄推送）
> 更新：2026-07-27
> 范围：Conductor → 第三方中台（适配器）→ 跨境平台

---

本计划只定义第一阶段的单向薄内容包推送。中台作为长期事实源、内部 Listing 与渠道版本、运营数据、反向拉取和复盘闭环，按 [双向同步与版本复盘计划](./双向同步与版本复盘计划.md) 实施；两者发生范围重叠时，后者作为目标架构。

## 1. 为什么做

目标只有一件事：**让 AI 产出的内容出现在电商平台上。**

中台的作用是 **适配器**：把 Conductor 的结构化内容，转成指定平台能接受的格式/接口。  
账号店铺、类目属性、价格库存、提交刊登、状态管理等，属于 **中台自身业务**，不是适配器职责，也不由 Conductor 承担。

默认链路：

```text
Conductor 生产内容  →  结构化包 POST 到中台  →  中台适配并走自有刊登业务  →  平台展示
```

---

## 2. 术语

| 说法 | 含义 |
| --- | --- |
| **Conductor** | 本仓库：内容生产、`output/` 归档、物料浏览器 |
| **中台** | 第三方系统：适配 AI 内容 + 自有刊登业务 |
| **平台** | Temu、Amazon、Shopify 等跨境电商平台 |
| **内容包** | Conductor 导出的薄 JSON（+ 媒体文件） |

---

## 3. 职责边界

| 谁 | 做什么 | 不做什么 |
| --- | --- | --- |
| Conductor | 生产文案/图/视频；组装薄包；人确认后 POST；本地记录推送状态 | 调平台 OpenAPI；管店铺/价格/库存；解析刊登成败 |
| 中台·适配器 | 接收包；映射为平台内容格式 | — |
| 中台·业务 | 店铺、类目、价格、提交、状态 | — |
| 平台 | 展示与售卖 | — |

面向人的聊天简版、完整生产报告、`output/` 人工验收流程保持不变；内容包是给中台的机器契约，不是替代人工报告。

## 4. 内容包结构

### 4.1 原则

- 结构化导出，字段尽量少。
- 只放「买家可见内容」+「对上号所需最少标识」。
- 不塞商品档案全表、供应链、利润、合规、16 章报告、刊登结果。

### 4.2 本地完整包

保存在对应 Listing 目录（建议路径：`{output_dir}/中台/content-package.json`）。

```json
{
  "metadata": {
    "listing_id": "MUG-RED-11OZ",
    "output_dir": "output/Temu-US/MUG-RED-11OZ",
    "recommended_platforms": ["Temu"],
    "market": "US",
    "skus": [{ "sku": "MUG-RED-11OZ", "qty": 1 }],
    "produced_at": "2026-07-27T12:00:00+08:00"
  },
  "copywriting": {
    "title": "...",
    "bullets": ["...", "..."],
    "description": "...",
    "keywords": ["...", "..."]
  },
  "images": [
    { "role": "main", "path": "图片/01-main.jpg", "order": 1 },
    { "role": "scene", "path": "图片/02-scene.jpg", "order": 2 }
  ],
  "video": null,
  "push": {
    "pushed": false,
    "pushed_at": null,
    "ok": null,
    "package_id": null,
    "last_error": null
  }
}
```

### 4.3 字段说明

| 块 / 字段 | 说明 |
| --- | --- |
| `metadata.recommended_platforms` | 推荐平台（数组）。真正推哪个由中台业务决定 |
| `metadata.market` | 本包文案/图按哪个市场写的（内容市场） |
| `metadata.listing_id` / `skus` / `output_dir` | 对上号、定位本地产物 |
| `copywriting` | 标题、要点、描述、关键词；某平台没有的字段用空数组或空字符串 |
| `images` | 有序列表；`path` 相对 `output_dir` |
| `video` | 没有则 `null`；首期可不传实体视频 |
| `push` | **仅本地**。是否已推、时间、成败、中台 `package_id`、错误信息 |

### 4.4 出站包

`POST` 时去掉 `push`，只发：

```json
{
  "metadata": { },
  "copywriting": { },
  "images": [ ],
  "video": null
}
```

媒体与 JSON 一并提交（首期建议 `multipart/form-data`：一个 JSON 字段 + 按 `images[].path` 对应的文件）。

## 5. 推送方式

### 5.1 API

```text
POST /api/v1/content-packages
```

成功示例：

```json
{
  "ok": true,
  "package_id": "中台侧id",
  "received_at": "..."
}
```

失败：`ok: false` + `message`。  
不返回平台 `item_id` 或刊登结果（属中台业务）。

鉴权、multipart 字段名、再次推送是更新还是新建：实现时与中台约定即可。

### 5.2 推送后写回

用中台响应更新本地包内 `push`，例如：

```json
"push": {
  "pushed": true,
  "pushed_at": "2026-07-27T12:05:00+08:00",
  "ok": true,
  "package_id": "中台返回的id",
  "last_error": null
}
```

已推过再推：提示「已推送过，是否再次推送？」确认后再发。

## 6. 人如何触发

推送会产生外部影响，必须确认后再 `POST`。

### 6.1 本轮（聊天 / 选择器）— 当场一次机会

内容生产完成后，下一步动作中增加：

```text
选择下一步动作：
1. 修改本轮文案
2. 重生成指定图片
3. 推送到中台
4. 查看本轮产物
```

- 有 UI 选择器：点「推送到中台」
- 无弹窗：输入对应数字
- 再确认一次，例如：「将把本轮 metadata + copywriting + images 推送到中台，确认吗？」
- 确认后才真正 `POST`

对话关闭且未推 = 放弃本轮聊天入口，改走浏览端。

### 6.2 补救（物料浏览器）

漏推或对话已关时，在 Conductor 物料浏览器打开该 Listing：

- 查看内容与 `push` 状态
- 点「推送到中台」→ 同样确认 → `POST` → 写回 `push`

聊天与浏览端共用同一本地包与同一套推送逻辑。
